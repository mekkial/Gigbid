GigBid: engineering design review

AI-4016 R&D Assignment II · individual submission · every claim points to a results file, a test, or a commit · negative and invalid results are reported as such

1. Problem and constraints

Workflow. A freelancer scans feeds, spends paid Connects on jobs they are unlikely to win, sends generic proposals, and meets scams. GigBid does discovery, assessment and drafting; the freelancer decides. Never automated: sending a proposal or message, spending Connects, accepting an offer or changing a price after approval, scraping any site, or claiming experience the portfolio does not show.

Constraints I actually worked under (they shape every result below): (i) hosted open models on Groq's free tier, which allows only 8,000 tokens/minute and 200,000 tokens/day per model; I exhausted the daily quota of two models during evaluation, so the later experiments use a local 8B model and small samples; (ii) a 16 GB laptop (no GPU server); (iii) the instructor's GigSim and persona data were not available, so the simulator and corpus are mine (docs/DATA_CARD.md); (iv) no Docker/deploy infrastructure at the start.

2. Architecture

Two hand-written LangGraph graphs share one typed-state discipline. Bid graph (one thread per job): intake, then Job Analyst, Risk Assessor and Fit Matcher in parallel (Send), a decision node (rule shared with the evaluation: agent/nodes/decision.py), Pricing, Writer, Claim Verifier, Critic (at most two revisions), Compliance Guard, interrupt() for human approval, then an idempotent submit. Conversation graph: read messages, classify intent, draft a reply or interview slots, interrupt, send. All agent I/O goes through one MarketplacePort (GigSim or live Upwork adapter, switched by config) and MCP tools: three servers I wrote (Portfolio read-only; Marketplace read+write with idempotency keys, dry-run, bearer auth, rate limit and an append-only audit log; Workspace for slots and email drafts) plus the official Upwork and GitHub servers (adapters tested against fakes only). Each agent has a tool allowlist.

State, trace and memory are kept apart. State is what this job needs now (reducers on parallel writes). The trace (per-node latency, tokens, cost; OpenTelemetry spans to Phoenix sharing one gigbid.trace_id with the MCP audit log) is for audit. Long-term memory (style rules, outcome statistics) is written only by explicit promotion rules (agent/memory/promotion_rules.py); raw tool output never enters it. Durability: Postgres checkpointer, so approvals survive a restart and submit exactly once.

3. R&D question A: does tool granularity change agent behaviour?

Hypotheses (docs/adr/0003-tool-granularity.md, written before the run): many fine-grained tools lower selection accuracy, especially on the small model; a few coarse tools keep selection high but lower argument accuracy; the tuned set wins on arguments and prompt tokens. Setup: 40 tasks with known-correct first calls; three toolsets (37 fine-grained tools with terse descriptions, 4 coarse action+params tools, my 15 real tools with rewritten descriptions); two open models; arguments are value-matched so naming differences are not penalised.

Reading. Prompt cost scales with tool count: the 37-tool set costs about 3.4x the tokens of the 4-tool set on the same model. On the small model, the tuned set is best on both metrics (see table), and coarse tools lose on argument accuracy, as hypothesised; on the stronger model fine-grained and coarse sets are within one or two tasks of each other, so with n=40 I cannot claim a difference. Cells with many API errors (rate limiting) are marked invalid and are not used for conclusions; the mid-model tuned cell was contaminated this way and is re-run when quota allows. Conclusion: granularity matters mostly for small models and for cost; it is not a free win for a strong model. Tool descriptions rewritten for the tuned set were not ablated separately from granularity.

6. The change request

The instructor's update was not available, so I simulated one with both ingredients (docs/CHANGE_REQUEST.md): a new rule (every proposal must disclose AI assistance) and a new cost (jobs under $500 cost +2 Connects). The simulated platform edit to GigSim (commit ff32a4c) is not counted. GigBid-side change: 5 lines in 2 files (policy_rules.yaml +2, agent/nodes/compliance.py +3) plus a 20-line test; the Connects change needed 0 lines because pricing, the dry-run preview and the approval screen read the platform's effective cost. No prompt, graph, UI or API change. What this says about the design: compliance rules are data and the Compliance Guard also re-checks human edits, so one change covers generated and edited text; the cost change was free only because the port returns the platform's effective cost instead of GigBid recomputing it. A rule that needs reasoning would not be absorbed this cheaply. I wrote GigSim, so I knew where the seams were: this measures the architecture, not surprise.

7. Signature extension: X3 Portfolio builder

A GitHub repo (via the official GitHub MCP server, or a local folder for private code) becomes a case study in which every claim is verified against the code before publication (agent/extensions/portfolio_builder.py, docs/EXTENSION.md): a cited file must exist; a skill must literally appear in the code or manifests; a “result” must contain a number that appears in the repo (impact claims without numbers are never published); survivors are graded by the claim verifier. Published items are indexed incrementally and become retrievable by the Portfolio server at once.

Measured: unit tests with a deliberately lying draft (fabricated skill, fabricated 80% result, citation of a non-existent file, injected “founded a unicorn startup”): all removed, 3 of 6 claims published (tests/unit/test_portfolio_builder.py). Not measured: verified-claim rate and retrieval gain on real repositories (no GitHub token or repository list was available while the machine was unattended); the GitHub MCP path is tested with a fake server only. Limit: “verified against the code” proves a claim is present in the repo, not that the freelancer wrote it (a fork would pass).

9. Safety and platform respect

GigBid must never: send or spend without a human approving in the UI; scrape or automate a site (live access is only the official Upwork MCP server, and live mode creates drafts the user confirms on Upwork); follow instructions inside a job post or client message; claim experience the portfolio does not show; include contact details, off-platform payment or guarantees; poll faster than 180 minutes in live mode; log emails, phone numbers or tokens. Enforced by: interrupt() before every external write and thread-derived idempotency keys; marketplace MCP bearer auth, per-user rate limit and append-only audit; untrusted-text delimiters, a SECURITY clause in every prompt, a deterministic injection scan, the policy-pack Compliance Guard (which also re-checks human edits); PII masking in logs/audit; encrypted per-user OAuth tokens; every query scoped by user.

What still gets through (stated, with a test for the first): (1) a scam whose only signals sit inside an instruction-looking sentence is flagged but not auto-skipped (tests/unit/test_risk_scan.py); (2) obfuscated contact details (“w h a t s a p p”, spelled-out numbers) evade the regex rules; (3) multi-turn or gradual attacks and instructions inside attachments are not tested; (4) evidence poisoning through an uploaded portfolio file; (5) the LLM judge and verifier are themselves promptable. One optimisation that helped (evals/results/optimisation.json): prompt trimming (writer/verifier evidence limited to 6 items x 600 chars) cut evidence tokens per prompt by 34.7%. One that did not help much: running the Fit Matcher's per-requirement searches concurrently gave only 1.11x in-process because retrieval is CPU-bound. Earlier concurrent evaluation runs showed p95 ≈ 120 s per analysed job: that was queueing behind my own token limiter, not per-job latency, which is why the budget run is sequential. On the free hosted tier the 200,000-tokens/day cap (about a dozen proposals per model per day) means the hosted open profile cannot serve a grading run without paid quota; I state that as a result, not an excuse.
