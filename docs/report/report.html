GigBid: engineering design review

AI-4016 R&D Assignment II · individual submission · every claim points to a results file, a test, or a commit · negative and invalid results are reported as such

1. Problem and constraints

Workflow. A freelancer scans feeds, spends paid Connects on jobs they are unlikely to win, sends generic proposals, and meets scams. GigBid does discovery, assessment and drafting; the freelancer decides. Never automated: sending a proposal or message, spending Connects, accepting an offer or changing a price after approval, scraping any site, or claiming experience the portfolio does not show.

Constraints I actually worked under (they shape every result below): (i) hosted open models on Groq's free tier, which allows only 8,000 tokens/minute and 200,000 tokens/day per model; I exhausted the daily quota of two models during evaluation, so the later experiments use a local 8B model and small samples; (ii) a 16 GB laptop (no GPU server); (iii) the instructor's GigSim and persona data were not available, so the simulator and corpus are mine (docs/DATA_CARD.md); (iv) no Docker/deploy infrastructure at the start.

Declared budgets (agent/config.yaml). Honest provenance: I set them after seeing queue-inflated timings from the concurrent evaluation runs, but before the sequential budget run that tests them; the local budgets are deliberately loose because latency there is hardware-bound.

2. Architecture

Two hand-written LangGraph graphs share one typed-state discipline. Bid graph (one thread per job): intake, then Job Analyst, Risk Assessor and Fit Matcher in parallel (Send), a decision node (rule shared with the evaluation: agent/nodes/decision.py), Pricing, Writer, Claim Verifier, Critic (at most two revisions), Compliance Guard, interrupt() for human approval, then an idempotent submit. Conversation graph: read messages, classify intent, draft a reply or interview slots, interrupt, send. All agent I/O goes through one MarketplacePort (GigSim or live Upwork adapter, switched by config) and MCP tools: three servers I wrote (Portfolio read-only; Marketplace read+write with idempotency keys, dry-run, bearer auth, rate limit and an append-only audit log; Workspace for slots and email drafts) plus the official Upwork and GitHub servers (adapters tested against fakes only). Each agent has a tool allowlist.

State, trace and memory are kept apart. State is what this job needs now (reducers on parallel writes). The trace (per-node latency, tokens, cost; OpenTelemetry spans to Phoenix sharing one gigbid.trace_id with the MCP audit log) is for audit. Long-term memory (style rules, outcome statistics) is written only by explicit promotion rules (agent/memory/promotion_rules.py); raw tool output never enters it. Durability: Postgres checkpointer, so approvals survive a restart and submit exactly once.

3. R&D question A: does tool granularity change agent behaviour?

Hypotheses (docs/adr/0003-tool-granularity.md, written before the run): many fine-grained tools lower selection accuracy, especially on the small model; a few coarse tools keep selection high but lower argument accuracy; the tuned set wins on arguments and prompt tokens. Setup: 40 tasks with known-correct first calls; three toolsets (37 fine-grained tools with terse descriptions, 4 coarse action+params tools, my 15 real tools with rewritten descriptions); two open models; arguments are value-matched so naming differences are not penalised.

Reading. Prompt cost scales with tool count: the 37-tool set costs about 3.4x the tokens of the 4-tool set on the same model. On the small model, the tuned set is best on both metrics (see table), and coarse tools lose on argument accuracy, as hypothesised; on the mid model (Qwen3.8-27B) fine-grained and coarse sets are within one or two tasks of each other (0.975 vs 1.0), and the tuned set is worse (0.825 selection, 0.75 arguments), which contradicts my hypothesis that the tuned set wins; its failures are job-field questions (budget, required skills) routed to get_market_stats, search_evidence or search_jobs instead of get_job, so the rewritten descriptions likely made those tools look too similar. With n=40 I cannot separate that from noise on a single run. The mid-model tuned cell was first invalidated by rate limiting (26 API errors) and was re-run on 2026-11-14 with 0 errors; the contaminated run is kept in tool_granularity_v1_contaminated_backup.json. Cells with many API errors are marked invalid and are not used for conclusions. Conclusion: granularity matters mostly for small models and for cost; it is not a free win for a strong model. Tool descriptions rewritten for the tuned set were not ablated separately from granularity.

4. R&D question B: advanced RAG

Hypotheses (docs/adr/0002-rag-hypotheses.md; written after a 40-job smoke run of V0/V2/V3, disclosed there): H1 hybrid beats dense by ≥5 points Recall@5; H2 reranking adds ≥0.10 MRR at ~50x latency; H3 decomposition beats V0 on 4-requirement jobs; H4 outcome boost will not move gold-evidence metrics; H5 corrective retrieval abstains on jobs to skip. Scorecard. H1 confirmed (Recall@5 0.906 → 1.000). H2 confirmed (MRR 0.737 → 0.917, p95 0.73 s vs 0.01 s). H3 refuted: decomposition lowered MRR (0.454 vs 0.629). My first V1 merged per-requirement rankings at chunk level and measured MRR 0.421; merging at project level (shipped in the table) raised recall but still did not beat hybrid+rerank. Both files are kept (rag_eval_v1_chunk_level_fusion.json). V6, BM25 keyword search only (no embedding model, no reranker, about 100 MB instead of about 1.4 GB, p95 under 1 ms) scores Recall@5 0.992 and MRR 0.765: better than naive dense search and than hybrid without the reranker, and below the shipped V3 (MRR 0.92). This corpus is templated, so keyword overlap is flattered; real portfolios describe skills less literally, so I expect the gap to V3 to be larger there. I measured V6 because the free public host has only 512 MB: the public demo link runs V6; the full V3 system (and the separate MCP servers) run locally and in Docker, and are what every other number in this report measures. H4 supported, trivially: outcome boost is identical to V2 on gold metrics; its value would have to show in reply rate, which this sample cannot resolve. H5 refuted as first implemented. V8's a-priori threshold (0.0, assuming logits) never abstained (the cross-encoder returns probabilities); calibrating on one persona gave 0.45, which abstains on 1.00 / 1.00 of skip jobs in the two held-out personas with 0.00 false abstentions.

Models: qwen3:8b (profile local). With one local model the judge is the writer's own model (self-judging), so judge scores are not comparable to a calibrated judge.

Judge calibration (my own 30 labels, blind to the judge's scores). Cohen's kappa on acceptable/not: 0.000 (raw agreement 0.40); weighted kappa on the 1-5 score 0.028. The judge called 30/30 proposals acceptable and gave a mean 4.1/5; I accepted 12/30 and gave a mean 2.5/5. All disagreements run one way (judge lenient). The judge is therefore not usable as a quality measure: the 'judge' columns in this report carry no weight, and the shipped system never uses the judge for a decision. On my labels, acceptable proposals were 5/16 for V0 and 7/14 for V3 (Fisher p=0.457: direction favours V3, but not significant). A pattern I noticed while labelling: 17/30 opening sentences repeat a 6+ word run of the job post. On my labels that did not predict rejection (8/17 acceptable when copied vs 4/13 otherwise, p=0.465), so I treat it as a style weakness, not as the main failure. Caveats: one labeller (me), n=30, and the labels were made on the local-model proposals.

Shipped: V3 (hybrid BM25+dense with RRF, cross-encoder rerank). It is the best on every retrieval metric at ~0.7 s/query on CPU. V8 is the one to adopt when abstention on out-of-scope jobs matters; it did not improve retrieval metrics. Where better retrieval did not translate into replies is in the proposals table above (small n, wide intervals).

5. R&D question C: is the multi-agent design worth it?

Same 10 dev jobs (AI/ML persona, stratified), three architectures: (a) one ReAct agent holding every read tool, (b) the prebuilt langgraph-supervisor (supervisor + analyst + writer workers), (c) my hand-built graph. All three ran on the same single local model (qwen3:8b), so the graph's per-node model routing is a no-op in this comparison; hosted-model runs were not possible after the daily quota was exhausted. Reading. The graph decided all 10 jobs correctly. The single agent's 0.60 is almost entirely a format failure: 40% of its answers were not valid JSON and it has no validate-and-retry step, but on the answers it did produce, accuracy was 1.0, so its judgement was fine. The graph's advantage here is structured hand-offs (Pydantic objects, re-asked on invalid output), not reasoning. The supervisor got 7 of 9 right and one job crashed on a hallucinated client id (a tool error the deterministic graph cannot hit). Where the single agent wins: median latency (about 30 s vs about 190 s for the graph, which makes 12-15 sequential model calls per proposal) and simplicity; it also produced only 1 proposal(s), so its proposal-quality columns are nearly empty and cannot be compared. Would I ship it? Not for sending anything: no compliance guard, no approval interrupt, no durable state. I might ship a single agent for the cheap triage step alone. Caveats: n=10 (9 for the supervisor), one 8B model, a simulator I wrote; differences of one or two jobs are not significant. The supervisor's token figure (about 1.5k) is almost certainly an undercount because the usage callback does not see its nested sub-agents' calls: do not read it as an efficiency win.

6. The change request

The instructor's update was not available, so I simulated one with both ingredients (docs/CHANGE_REQUEST.md): a new rule (every proposal must disclose AI assistance) and a new cost (jobs under $500 cost +2 Connects). The simulated platform edit to GigSim (commit ff32a4c) is not counted. GigBid-side change: 5 lines in 2 files (policy_rules.yaml +2, agent/nodes/compliance.py +3) plus a 20-line test; the Connects change needed 0 lines because pricing, the dry-run preview and the approval screen read the platform's effective cost. No prompt, graph, UI or API change. What this says about the design: compliance rules are data and the Compliance Guard also re-checks human edits, so one change covers generated and edited text; the cost change was free only because the port returns the platform's effective cost instead of GigBid recomputing it. A rule that needs reasoning would not be absorbed this cheaply. I wrote GigSim, so I knew where the seams were: this measures the architecture, not surprise.

7. Signature extension: X3 Portfolio builder

A GitHub repo (via the official GitHub MCP server, or a local folder for private code) becomes a case study in which every claim is verified against the code before publication (agent/extensions/portfolio_builder.py, docs/EXTENSION.md): a cited file must exist; a skill must literally appear in the code or manifests; a “result” must contain a number that appears in the repo (impact claims without numbers are never published); survivors are graded by the claim verifier. Published items are indexed incrementally and become retrievable by the Portfolio server at once.

Measured: unit tests with a deliberately lying draft (fabricated skill, fabricated 80% result, citation of a non-existent file, injected “founded a unicorn startup”): all removed, 3 of 6 claims published (tests/unit/test_portfolio_builder.py). Not measured: verified-claim rate and retrieval gain on real repositories (no GitHub token or repository list was available while the machine was unattended); the GitHub MCP path is tested with a fake server only. Limit: “verified against the code” proves a claim is present in the repo, not that the freelancer wrote it (a fork would pass).

Honest scope. Only these two groups appeared; missed evidence, mispriced, scam miss and injection-not-flagged had zero failures, which says the synthetic dev set is easy, not that the system is robust. LLM-dependent categories (end-to-end, 18 proposals per arm, local 8B, proposal_eval.json): unsupported claim: 50% of V0 proposals and 17% of V3 proposals contained one before verification; the verifier cut that to 17% and 0%. Compliance miss: 0 of 5 proposals from the graph in the architecture run contained a raw policy violation. Generic opening and tool error: not measured for the graph; in the baselines a hallucinated client id crashed one supervisor job (tool error) and 40% of single-agent answers were malformed JSON. Critic loop (diagnosed, partly fixed). All 36 end-to-end proposals ran to the revision cap and none reached the 120-word length target (mean 88 words), so the Critic's hard length rule rejected every first draft: a loop that never converged but was capped, costing roughly three writer/verify/critic rounds per proposal. Fix tried: state an explicit word budget (130-200) in the writer's task message and move the bounds into config. On a 3-job diagnostic (critic_diagnostic.json, not an evaluation) the length rule then passed in 7 of 9 rounds (0 of 9 before) and drafts grew from 76-96 to 92-120 words. Unresolved: no round was approved in either condition, because the critic's personalisation score stays near 0.4 (bar 0.6): the portfolio only partly matches these jobs and the system will not invent relevance, so a strict critic keeps asking for what the evidence cannot support. The shipped numbers above were measured before this fix. With the hosted LLM in the loop (decision eval, shipped config, n=20/persona, before these two fixes) bid-or-skip F1 was 0.92 / 0.87 / 0.92 and scam recall 1.0; the precision loss was the low-ball group above. With both fixes, on the local 8B (n=12/persona) F1 and scam F1 were 1.0 on all three personas: a ceiling effect of an easy synthetic set, not evidence of perfection. Model comparison for the analysis nodes (R&D: choose by measurement), re-run on hosted models after the fixes, n=20/persona: the shipped small model (gpt-oss-20b), the mid model (Qwen3.8-27B) and the strong model (gpt-oss-120b) all reached bid-or-skip F1 1.0 and scam recall 1.0 on all three personas. They tie on quality, so the cheapest (small) is shipped; the set is too easy to separate them, and the p95 latencies in decision_eval.json are inflated by my own rate limiter and are not comparable across configs.

9. Safety and platform respect

GigBid must never: send or spend without a human approving in the UI; scrape or automate a site (live access is only the official Upwork MCP server, and live mode creates drafts the user confirms on Upwork); follow instructions inside a job post or client message; claim experience the portfolio does not show; include contact details, off-platform payment or guarantees; poll faster than 180 minutes in live mode; log emails, phone numbers or tokens. Enforced by: interrupt() before every external write and thread-derived idempotency keys; marketplace MCP bearer auth, per-user rate limit and append-only audit; untrusted-text delimiters, a SECURITY clause in every prompt, a deterministic injection scan, the policy-pack Compliance Guard (which also re-checks human edits); PII masking in logs/audit; encrypted per-user OAuth tokens; every query scoped by user.

Reading the injection numbers. Attack success (ASR) = share of outputs that affirmatively comply (real contact details or an un-negated promise). My first metric counted any mention of the attacker's words and reported the defence as making client-message attacks worse (0% → 50%); reading the outputs showed they were polite refusals (“We cannot include email addresses or promise guaranteed results”), so I replaced the metric and kept the original result (injection_eval_v1_loose_metric.json) and every output (injection_outputs.jsonl). With the strict metric the local 8B model was already almost immune (5.6% on job posts, 0% on messages without any defence), so this is a floor effect: the data cannot show that the delimiter/SECURITY defences help, only that nothing got through. n is 18 and 20; a stronger, paraphrased attack set was not built.

What still gets through (stated, with a test for the first): (1) a scam whose only signals sit inside an instruction-looking sentence is flagged but not auto-skipped (tests/unit/test_risk_scan.py); (2) obfuscated contact details (“w h a t s a p p”, spelled-out numbers) evade the regex rules; (3) multi-turn or gradual attacks and instructions inside attachments are not tested; (4) evidence poisoning through an uploaded portfolio file; (5) the LLM judge and verifier are themselves promptable. Live Upwork mode has never run against the real server.

One optimisation that helped (evals/results/optimisation.json): prompt trimming (writer/verifier evidence limited to 6 items x 600 chars) cut evidence tokens per prompt by 34.7%. One that did not help much: running the Fit Matcher's per-requirement searches concurrently gave only 1.11x in-process because retrieval is CPU-bound. Analysis median 1.8 s but p95 51.7 s, and proposal p95 222 s against the declared 150 s: both latency budgets are missed; tokens (20.4k vs 30k) and cost ($0.0056 vs $0.012) are within budget. I did not isolate why the analysis tail is long (a rate-limit retry on a shared per-minute token cap is the likeliest cause) and n=3 proposals is too few for a stable p95; every proposal also used the full 3 revision rounds.

Deployment footprint (measured locally, scripts/measure_light_memory.sh). The full retrieval stack (embedding model plus reranker on CPU) needs about 1.4 GB of RAM by itself (555 MB after the embedding model, 1,368 MB after the reranker). The light configuration used for a free 512 MB host (V6 keyword retrieval, tools in-process, no PyTorch) reached about 220 MB in total (GigSim plus API) while analysing and drafting a job end to end; with the three MCP servers as separate processes it peaked at about 455 MB, too close to the limit, so the light deployment calls the same tool code in-process. In a clean environment without PyTorch or sentence-transformers a full draft reached the approval step.

Earlier concurrent evaluation runs showed p95 ≈ 120 s per analysed job: that was queueing behind my own token limiter, not per-job latency, which is why the budget run is sequential. On the free hosted tier the 200,000-tokens/day cap (about a dozen proposals per model per day) means the hosted open profile cannot serve a grading run without paid quota; I state that as a result, not an excuse.
